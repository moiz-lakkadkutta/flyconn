## A. Whole-brain LIF simulation codebases

### A1. philshiu/Drosophila_brain_model (the reference implementation)

URL: https://github.com/philshiu/Drosophila_brain_model | License: MIT (LICENSE: "Copyright (c) 2023 Philip Shiu and Nico Spiller") | Stars 347, forks 72, open issues 2, contributors 3 (GitHub API 2026-09-26) | Created 2023-02-25, last push / last commit **2024-09-14** | Language: Jupyter Notebook + Python (`model.py` 12 KB, `utils.py` 2 KB).

Facts read from the local clone (`scratchpad/repos/shiu`):

- **Brian2 pin**: `environment.yml` pins `python=3.10`, `brian2=2.5.1`, `numpy=1.24` (+ jupyter, pandas, joblib, pyarrow). `environment_full.yml` (the exact env used for the paper) has `brian2=2.5.1=py310hc781a3c_0`, `cython=0.29.33`, `gsl=2.7`, i.e. Brian2 was running with the Cython runtime code-generation target, not standalone mode.
- **Input data files** (Readme + `example.ipynb` cell 2): `2023_03_23_completeness_630_final.csv` (one row per neuron, index = FlyWire root id; the row order defines the Brian index) and `2023_03_23_connectivity_630_final.parquet` (columns `Presynaptic_ID, Postsynaptic_ID, Presynaptic_Index, Postsynaptic_Index, Connectivity, Excitatory, Excitatory x Connectivity`). They are FlyWire materialization v630 exports built by the authors (issue #6 "Request for Code to Generate Connectivity Data Files" is closed; the generating code is not in the repo). The Readme also ships v783 files `Completeness_783.csv` / `Connectivity_783.parquet` and says: "The code is currently set up for the Flywire version 630, which the paper used. To use public version 783, change the config dictionary".
- **Model construction** (`model.py` `create_model`): `NeuronGroup(N=len(df_comp), model=eqs, method='linear', threshold='v > v_th', reset='v = v_rst; w = 0; g = 0 * mV', refractory='rfc')`; `Synapses(neu, neu, 'w : volt', on_pre='g += w', delay=t_dly)`; `syn.connect(i=Presynaptic_Index, j=Postsynaptic_Index)`; `syn.w = df_con['Excitatory x Connectivity'] * w_syn`.
- **Sign derivation**: signs are NOT computed in this repo; they arrive pre-baked in the parquet column `Excitatory` (+1/−1) and its product `Excitatory x Connectivity`. The rule (paper Methods, already captured in `golden_results_raw.md` A2) is GABA/Glu ⇒ −1 for the whole neuron, everything else ⇒ +1, by majority of per-synapse NT predictions with cleft score ≥ 50.
- **Integration method / dt**: `method='linear'` and **no `defaultclock.dt` is set anywhere in `model.py`, `utils.py` or the notebook**, so Brian2's default `dt = 0.1 ms` applies (Brian2 docs: https://brian2.readthedocs.io/en/stable/user/running.html, "defaultclock ... dt = 0.1*ms" — see A5). In Brian2, `'linear'` is the legacy name for the `'exact'` state updater (see A5): the two linear ODEs `dv/dt=(v_0-v+g)/t_mbr`, `dg/dt=-g/tau` are integrated **exactly** (closed-form matrix exponential per step), with threshold tested after the update, spikes delivered with a fixed 18-step delay (1.8 ms / 0.1 ms) and the reset zeroing both `v` and `g`. **Implication for spike-for-spike parity**: a PyTorch engine must (i) use the closed-form coefficients `exp(-dt/t_mbr)`, `exp(-dt/tau)` and the exact cross term for `g→v` (the ref64 oracle in drosophila-brain-mlx transcribes exactly these, see A3), not forward Euler; (ii) reproduce Brian2's scheduling slot order (`start, groups, thresholds, synapses, resets, end`) including the 18-step delay ring buffer; (iii) match the `(unless refractory)` semantics, under which **both** `v` and `g` are frozen during the 2.2 ms (= 22 steps) refractory window, and the refractory period is 0 for Poisson-driven neurons (`neu[i].rfc = 0*ms`).
- **Poisson drive**: `PoissonInput(target=neu[i], target_var='v', N=1, rate=r_poi, weight=w_syn*f_poi)` — each Poisson event adds 68.75 mV directly to `v`, so one event ⇒ one spike. Brian2's `PoissonInput` draws a binomial per step (`N=1` ⇒ Bernoulli with p = rate·dt), so RNG streams cannot be matched across simulators; parity must be tested with a **fixed input spike train** (as drosophila-brain-mlx does) rather than with matched seeds.
- **Silencing**: `silence()` zeroes only **outgoing** weights (`syn.w[' {} == i'] = 0*mV`), contradicting the Readme's "to and from" (open issue #10).
- **Trials**: `run_exp` uses joblib `loky` to run `n_run=30` independent 1 s trials in separate processes; each trial rebuilds the whole network (`create_model` is called per trial). No seeding anywhere ⇒ runs are not reproducible bit-for-bit.
- **What `example.ipynb` reproduces**: it (1) activates the 21 right-labellum sugar GRNs at the default 200 Hz (`r_poi` is 150 Hz in `default_params` but the notebook text says "By default, the neurons are excited at 200 Hz" — the notebook as shipped actually runs the `default_params` value; the discrepancy is worth noting), writes `results/example/sugarR.parquet` ("more than 400 000 spikes ... only about 400 neurons show activity"); (2) reruns at 100 Hz (`sugarR_100Hz`); (3) demonstrates `r_poi2` co-activation and (4) silencing, and converts spikes to rates with `utils.get_rate` (mean and s.d. over 30 trials). The paper-figure notebook `figures.ipynb` is referenced by the Readme but is not in the local clone; the multi-GB raw output lives at https://doi.org/10.17617/3.CZODIW.
- **Cross-check of constants vs `golden_results_raw.md` §A1**: `v_0 = -52 mV` (model.py `'v_0' : -52 * mV`) — agrees; `t_rfc = 2.2 ms` (`'t_rfc' : 2.2 * ms`) — agrees; `w_syn = 0.275 mV` (`'w_syn' : .275 * mV`) — agrees; `f_poi = 250`, `t_dly = 1.8 ms`, `method='linear'` — all agree with the table. No disagreement found.
- **Tests/CI**: none. **API quality**: two functions (`run_exp`, `get_rate`) with file-path based I/O; adequate for a paper, not a library. **Heavy deps**: brian2 (needs a C compiler for Cython target), joblib.
- **Gap vs flyconn**: FlyWire v630/v783 only, no MaleCNS/hemibrain/MANC/BANC, no signed-graph layer, no uncertainty, CPU only, per-trial network rebuild, no seeding, no tests.
- **Verdict: borrow-ideas + use as the parity oracle.** Depend on it only as the ground-truth generator inside a test harness (pin `brian2==2.5.1` for paper parity and also test against current 2.10.x); do not import `model.py` at runtime.

### A2. eonsystemspbc/fly-brain

URL: https://github.com/eonsystemspbc/fly-brain | Org: Eon Systems PBC (https://eon.systems, 5 public repos) | License: **GPL-2.0-or-later** (LICENSE = GPLv2 text; README: "GPL-2.0-or-later"; vendored Shiu code under `code/paper-phil-drosophila/` stays MIT) | Stars **920**, forks 128, open issues 0 | Created 2026-03-05, last push **2026-08-29** ("add LICENSE"); 15 commits total, all by a single author ("Alexis", not linked to a GitHub account, so the contributors API returns 0/1) | Language: Python.

What is actually in the repo (read from `scratchpad/repos/fly-brain`):

- Entry point `main.py` → `code/benchmark.py` (548 lines, orchestrator) dispatching to **six** runners, all real files: `code/run_brian2_cuda.py` (581 lines; Brian2 C++ standalone *and* Brian2CUDA `cuda_standalone`), `code/run_pytorch.py` (648), `code/run_nestgpu.py` (641; needs a from-source NEST GPU build with a custom `user_m1` CUDA neuron shipped in `scripts/nestgpu_source_files/`), `code/run_genn.py` (660; PyGeNN 5.4.0), `code/run_brian2_genn.py` (503; Brian2GeNN 1.7.0 in a *separate* conda env `environment-brian2genn.yml` because Brian2GeNN pins Brian2<2.6 while Brian2CUDA 1.0a7 needs Brian2 2.8.0). Comparison scripts: `code/compare_ground_truth.py`, `code/compare_spike_outputs.py`, `code/compare_backend_to_brian2.py`.
- **Purpose**: it is a **benchmark harness**, not a simulation library. Every runner is a `run_single_benchmark(t_run_sec, n_run, experiment, logger, ...)` that times setup/build/sim and dumps one parquet per grid point (`t_run ∈ {0.1,1,10,100} s × n_run ∈ {1,4,8,16,32}`), accumulating into `data/benchmark-results.csv` (720 rows on disk) for a manuscript the README calls "the Nature paper" (`--paper --run-label nature_2026_07`; publication status UNVERIFIED — see web check below). There is no importable model API, no CLI for arbitrary experiments beyond `--experiment {sugar,p9}`.
- **Data format**: the Shiu CSV/parquet pair, v783 (`data/2025_Completeness_783.csv`, `data/2025_Connectivity_783.parquet`; v630 in `data/archive/`). PyTorch caches a CSR/COO weight tensor to `weight_csr.pkl`.
- **PyTorch backend details** (`code/run_pytorch.py`): `DT = 0.1` ms; `LIFNeuron.forward` does `v = v + voltage_stim; v = v + (dt/tau_mem) * (conductance - (v - v_rest))` and `AlphaSynapse.forward` does `conductance*(1 - dt/tauSyn) + delayed_input` — i.e. **forward Euler, not Brian2's exact integrator**, so it cannot be spike-for-spike identical to Brian2 by construction (the README itself only claims Jaccard/rate-correlation agreement). Delay is a `torch.roll` ring buffer of `int(1.8/0.1)+1` slots; recurrent input is `torch.sparse.mm`-style CSR matmul on CUDA; trials are **batched** (`batch_size = n_run`, state tensors `[batch, N]`) — this is the one design idea worth taking. Device selection is `'cuda' if torch.cuda.is_available() else 'cpu'` — **no MPS path**. Poisson input is `torch.bernoulli(rates*dt/1000, generator=None)`; **no `manual_seed` anywhere in `run_pytorch.py` or `benchmark.py`** (only the GeNN/Brian2GeNN runners seed via `GENN_SEED`/`BRIAN2GENN_SEED`), so PyTorch runs are non-deterministic. The model has a surrogate-gradient (`ATan`) autograd function, unused by the benchmark.
- **Brian2 equivalence test**: no unit test. `compare_ground_truth.py` computes active-neuron Jaccard/precision/recall, per-neuron rate Pearson r, spike-count ratio and top deviations against `brian2cpp` parquet; `compare_spike_outputs.py` adds greedy spike-time matching within a tolerance window. The output `data/ground-truth-comparison.json` referenced by the README is **not committed**, and the 600-parquet result bundle is on Google Drive, so the achieved parity numbers are UNVERIFIED from the repo alone. `data/results/nature_2026_07/README.md` says PyTorch and NEST GPU outputs are "post-parity-fix runs", implying earlier mismatches.
- **Tests / CI**: none (`find . -name "test*"` → nothing; no `.github/`). **Platform**: README "System requirements: Linux (tested on Ubuntu 22.04 under WSL2), NVIDIA GPU with CUDA 12.x (RTX 4070)". `environment.yml` pulls `torch` from the cu126 index, `brian2cuda==1.0a7`, GeNN 5.4.0 from a zip.
- **Honest verdict — could it be our backend? No.** It is a GPL-2.0 benchmark script collection with a single author and a 5-month-quiet history; its PyTorch model is Euler-integrated, CUDA-or-CPU only, unseeded, has no tests and no library API. What we would have to add to make it usable: (1) replace Euler with the exact closed-form update; (2) MPS device path and MPS-safe sparse ops; (3) seeding/determinism; (4) a Python API decoupled from `benchmark.py`; (5) tests; (6) relicense concerns (GPL-2.0-or-later is incompatible with an MIT/BSD flyconn if we copy code). **Borrow-ideas**: trial batching along a leading dimension, the six-backend comparison methodology (Jaccard, rate r, spike-count ratio, tolerance-window spike matching), the parquet spike schema (`time_ms, trial, neuron_index, flywire_id, exp_name`), and the empirical warning that Brian2GeNN cannot batch independent trials.

### A3. Kisame76/drosophila-brain-mlx

URL: https://github.com/Kisame76/drosophila-brain-mlx | PyPI dist name `mlx-lif-engine` 0.1.0 (pyproject; not checked on PyPI) | License: MIT (LICENSE: "Copyright (c) 2026 Kiyan Doguc") | Stars 2, forks 0, open issues 0, contributors 1 | Created 2026-09-14, last push **2026-09-26** (very active; single author) | Python ≥3.11, deps `mlx>=0.32.0, numpy>=2.0, pyarrow>=18`; optional `brian2>=2.9.0, pandas` for validation, `pytest` for dev. 22 modules under `src/lif/` (4,905 lines) and 17 test files under `tests/`. No CI workflow.

- **Engines**: `engine_naive.py` (dense MLX, eval per tick), `engine_chunked.py` (dense MLX chunked), `engine_metal.py` (custom sparse Metal kernel via `mx.fast.metal_kernel`), `engine_fused.py` (two Metal dispatches per tick — the fast lane), `engine_ref64.py` (float64 NumPy oracle with identical tick semantics, needed "because Metal has no float64"). README: "**Not portable.** Apple silicon only; it depends on Metal."
- **Brian2 equivalence method and tolerance** (`src/lif/validate_brian2.py`, `tests/test_brian2.py`): runs Brian2 2.10.1 and the engine on a **connected 800-neuron subnetwork with a fixed (pre-drawn) input spike train**, "so no RNG difference can contaminate the comparison". Four configurations (500 ticks/4 seeds/150 Hz; 2,000/20/400 Hz; 2,000/40/800 Hz; 3,000/60/1,200 Hz). Gates: `test_ref64_spike_times_equal_brian2` asserts every `(neuron, time)` pair Brian2's `SpikeMonitor` records is reproduced **exactly** by the float64 oracle ("engine tick k converted as k * dt and no offset"); `test_fused_spike_times_are_within_float32_rounding` allows the float32 Metal lane to differ; the CLI `python -m lif.validate_brian2` "exits non-zero if ref64 differs from Brian2 at all or if the fused lane leaves out or adds more than **5 %** of Brian2's spikes". Reported results (README "Correctness" table): ref64 counts and spike times identical in all four configs; float32 lane counts identical in 3/4 and spike times off by 23–38 moved spikes out of 2,973–24,700 ("most moved spikes fire one tick early"). The closed-form coefficients in `src/lif/core.py` are "transcribed from the code Brian2 generates for `method='linear'`" (ATTRIBUTION.md). A second gate, `validate_notebook.py`, compares against the five parquet files upstream's `example.ipynb` produced, necessarily only at the rate level because Brian2's Poisson RNG differs.
- **Degree-preserving shuffle**: `src/lif/shuffle_pack.py` (153 lines). Method (docstring): every source neuron keeps its CSR row (out-degree and signed weights), destinations are permuted across all edges (so in-degrees are kept), then repeated destinations within a row are swapped with a uniformly chosen other edge's destination "until no row repeats one"; the manifest records `dataset=<name>-degree-shuffled-seed<N>`. Result shown in README: MN9 ≈ 67 Hz on real v630 wiring vs silent on shuffled wiring (seeds 0–4), with the sugar GRNs at ≈ 99 Hz in both.
- **MaleCNS-constants caveat** (exact wording, README "Two datasets" section): "Spike counts from the two packs are not comparable: different specimen, different laboratory, and the Shiu et al. constants were fitted to FlyWire." ATTRIBUTION.md: "The model constants are Shiu et al.'s and were fitted to FlyWire, not to this dataset; `src/lif/compile_pack_malecns.py` records that in the pack manifest." Node selection and signs follow the materialization `male-cns-v1.0-superclass-non-null-known-nt` (same as mehrantsi/flyBrain). MaleCNS is credited as CC BY 4.0.
- **Performance claims** (README, M4 Pro 24 GB, v630 127,400 neurons / 14,687,178 edges, 10,000 ticks = 1 s at dt 0.1 ms, 21 sugar GRNs at 150 Hz): fused lane **0.2933 s per biological second** (±0.0001, n=3, 665 MB); sparse Metal 0.7491; dense MLX 19.55–22.02; **Brian2 2.10.1 Cython 2.07 s** (numpy target 8.38 s) measured with `tools/bench_brian2.py` on the same machine ⇒ ~7×. With spike recording on, the fused lane costs +12.3 % (0.3313 s). mehrantsi/flyBrain Rust/Metal: 0.3769 s. MaleCNS pack (100 hub neurons at 150 Hz, 2,000 ticks): fused 1.1676 s/bio-s. The README is unusually candid about its own earlier measurement errors.
- **Determinism**: all four lanes give bit-identical per-neuron spike-count SHA-256 for the same stimulus and seed; trial `n` draws input with `seed + n`.
- **API**: `core.load_pack`, `core.make_stimulus_for(pack, ids, rate_hz, n_ticks, seed)`, `engine_fused.run(pack, stim, silenced=mask, chunk, edge_split, record)`, plus an upstream-compatible `experiment.run_exp(...)` and `names.py` for MaleCNS type/instance labels. Reasonable and small.
- **Gap vs flyconn**: Apple-Silicon-only (no CUDA, no CPU production path except the slow float64 oracle), single author, two datasets, no graph/uncertainty/YAML layers, no cross-dataset harmonization.
- **Verdict: borrow-ideas (heavily).** The fixed-spike-train Brian2 gate, the float64 oracle pattern, the pack manifest with provenance, the degree-preserving shuffle and the caveat wording are exactly what flyconn's parity test suite should copy (MIT, so attribution suffices). Do not depend on it: MLX is not our device story.

- **Apple Silicon**: 2.10.1 ships **4 `macosx_*_arm64` wheels** on PyPI (counted from the release file list). Release notes: "We now build and test on Apple Silicon (M1) hardware (#1501)" — Brian 2.6.0 (https://brian2.readthedocs.io/en/stable/introduction/release_notes.html). The Shiu pin 2.5.1 predates that; it installs on arm64 via conda-forge but is not tested upstream on M1. drosophila-brain-mlx ran Brian2 2.10.1 Cython on an M4 Pro (2.07 s per biological second for the full v630 model), so an Apple-Silicon Brian2 oracle is practical.
- **Cython vs standalone**: default runtime mode generates Cython per code object (needs a C++ compiler; install docs: "C++ code generation is highly recommended" and requires "a C++ compiler and Cython (automatically installed as a dependency of Brian)"); numpy target works without a compiler (4× slower in the MLX repo's measurement: 8.38 vs 2.07 s). C++ standalone mode (`set_device('cpp_standalone')`) compiles the whole network to one binary and is what eonsystems `run_brian2_cuda.py` uses for CPU and Brian2CUDA (`cuda_standalone`, PyPI `brian2cuda` 1.0b1 2025-12-05, GPL-3.0) for GPU. Standalone is markedly faster for long runs but network objects cannot be changed between `run()` calls without a rebuild — the reason eonsystems runs trials sequentially.
- **Default integration method for this LIF**: docs (https://brian2.readthedocs.io/en/stable/user/numerical_integration.html): "By default, Brian chooses an integration method automatically, trying to solve the equations exactly first (for linear equations)"; "NeuronGroup and Synapses will use the first suitable method out of the methods 'exact', 'euler' and 'heun'"; "'exact': exact integration for linear equations (alternative name: 'linear')". Release notes 2.1: "The `linear` state updater has been renamed to `exact` to avoid confusion (#877)". The alias survives in current source (`brian2/stateupdaters/exact.py`: `__all__ = ["linear", "exact", "independent"]`; `linear = LinearStateUpdater()`). So Shiu's explicit `method='linear'` and Brian2's automatic choice coincide: the v/g system is integrated **exactly** (sympy-derived closed form, evaluated each step), not with Euler. The tutorial output confirms the auto-choice for a plain LIF: "INFO No numerical integration method specified for group 'neurongroup', using method 'exact'".
- **Default dt**: `defaultclock.dt = 0.1 ms` (Brian2 source `brian2/devices/device.py`: `self.defaultclock = Clock(dt=0.1 * ms, name="defaultclock")` at line 381 on `main` and line 334 at tag 2.5.1, read via the GitHub contents API on 2026-09-26). The Shiu model never overrides it, so **dt = 0.1 ms, 10,000 steps per 1 s trial, synaptic delay = 18 steps, refractory = 22 steps**.
- **Schedule** (https://brian2.readthedocs.io/en/stable/user/running.html): default slot order `['start', 'groups', 'thresholds', 'synapses', 'resets', 'end']` — state update, then threshold test, then synaptic propagation (delayed spikes arriving this step increment `g`), then reset. A parity engine must apply the same order; the MLX repo's ref64 oracle demonstrates spike-for-spike agreement is achievable in float64.

### A6. PyTorch status and MPS sparse support (engine design input)

- **Current stable**: PyPI `torch` **2.14.0**, uploaded **2026-09-02** (2.13.0 on 2026-07-08; 2.12.1 on 2026-06-17) — https://pypi.org/pypi/torch/json.
- **Empirical MPS test run today** (`uv run --python 3.12 --with torch`, torch 2.14.0, macOS 26.2, arm64; script `scratchpad/mps_sparse_test.py`, N=1000, nnz=5000):
  - `torch.sparse_coo_tensor(...)` created directly on `mps` — **OK**; COO `.to('mps')` — **OK**; `torch.sparse.mm(coo_mps, dense)` — **OK**.
  - CSR: `.to_sparse_csr().to('mps')` — **FAIL** `NotImplementedError: Could not run 'new_compressed_tensor' from the 'mps:0' device` (the same error text as the 2024 tracking issue https://github.com/pytorch/pytorch/issues/129842, now closed; the broader request https://github.com/pytorch/pytorch/issues/140941 is "Closed as not planned"). **CSR/BSR layouts are still unsupported on MPS.**
  - `index_add_` — **OK**; `scatter_add_` — **OK**; `torch.bincount(weights=)` — **OK**. But with `torch.use_deterministic_algorithms(True)`, `index_add_` on MPS **FAILS**: "index_put_with_accumulate_mps does not have a deterministic implementation" — so scatter-based propagation on MPS is float-order nondeterministic (seohyunjun's README reports the same CPU/MPS bit-mismatch).
  - `float64` on MPS — **FAIL** ("the MPS framework doesn't support float64"), so the float64 oracle must run on CPU.
  - `torch.mps.manual_seed` + `torch.bernoulli` — OK (seedable Poisson drive).
  - The official MPS notes page (https://docs.pytorch.org/docs/2.14/notes/mps.html) says nothing about sparse layouts; PyTorch's own warning still labels CSR "beta".
- **Design consequence**: a cross-platform engine should represent the connectome as **COO (or edge-list) and use `torch.sparse.mm` with COO or gather+`index_add_`**, keep a CPU float64 reference path for parity tests, treat MPS float32 results as "within-rounding" (like drosophila-brain-mlx's 5 % gate) rather than bit-identical, and use CSR only on CPU/CUDA where it is faster. Bit-exact determinism should be claimed for CPU/float64 only.
